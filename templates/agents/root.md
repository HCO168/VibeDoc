## 1. Current State And Authority

- 用户沟通语言规则：除非用户明确要求使用其他语言，所有面向用户的说明、进度更新、结果汇报、问题澄清与开发沟通默认使用{{language}}。技术标识符、代码、命令、API 路径、字段名和必要的原始日志保持原文，不为改写语言而改动其技术含义。
- This is a shared workspace. Disk state is newer than memory, chat history, cached excerpts, or plans. Before editing, read the current target and only the callers, contracts, and docs needed for the task; do not repeatedly re-read unchanged context. Inspect results in proportion to risk. Change-log history is optional, never a prerequisite.
- Conflict priority: latest explicit user instruction; on-disk `AGENTS.md`; `{{rulesDir}}/*`; `{{docs.behavior}}/*`; API/table contracts in {{contracts}}; current source, migrations, and runtime config; other implementation docs; `{{docs.changelogs}}/*`; `{{docs.expired}}/*`. History never overrides current behavior or source.
- Before modifying a scoped area, read its nearest applicable local `AGENTS.md`; `{{docs.root}}/AGENTS.md` governs documentation and work tracking.
- If a target, contract, or runtime changes unexpectedly, preserve and re-read the new state before proceeding. Resolve a file conflict and merge directly when both intents are clear, all changes can be retained without changing a contract or discarding another person's work, and relevant checks can verify the result. Stop and ask when the intent is ambiguous, the requested behaviors are incompatible, or the merge cannot be verified safely. Clearly unrelated changes remain untouched.

## 2. Workspace Safety

- Use minimal, context-aware edits. Never replace a whole existing file from memory unless the user explicitly requests a full rewrite. Assume worktrees may be dirty; preserve unrelated staged and unstaged work. Never revert, discard, rewrite, or clean another person's changes. Do not amend commits or use destructive commands such as `git reset --hard` or `git checkout --` without explicit approval. Avoid broad formatting, generation, or replacement when a focused operation works.
- Align with the user before choosing among paths with material hidden consequences.
- 问题修复与方案评估规则：当用户要求修复问题，或已提出一个解决方案时，应按问题复杂度评估用户方案及其他必要的可行路径，说明适用条件、影响、风险和验证成本，并明确推荐方案及理由；不得将用户方案默认为唯一方案或已选方案。若选择会影响功能行为、数据、API/表结构契约、架构、权限、部署或其他实质性取舍，须等待用户选择后再修改。紧急安全或数据保护事件可先采取最小且可逆的隔离措施，随后立即给出方案与后续决策。
- Never permanently delete an entire existing file. Preserve a local recovery copy according to the applicable local instructions; it is recovery-only and must never be staged, committed, bundled, deployed, or served. Do not clear a recovery copy without explicit user approval.

## 3. Git And Collaboration

- Every owning repository uses `{{git.integration}}` for integration. Before a file-changing task, fetch the remote when present, verify the base includes `origin/{{git.integration}}`, and create a unique `{{git.branchPrefix}}<feature>` branch from latest `{{git.integration}}` in a separate worktree. Never switch a worktree used by another agent. If `{{git.integration}}` does not exist, get explicit approval before creating it from release `{{git.release}}`.
- Branches are promoted {{git.chain}}; `{{git.release}}` is release-only. Merge a branch into the next level only for an explicit release of that level, from a clean release worktree, after the previous level ran that exact state and after full release, migration, deployment, documentation, and rollback review. Never commit directly on a branch after `{{git.integration}}`, merge a feature or `{{git.integration}}` past its next level, or use those branches to synchronize feature work; release fixes land on `{{git.integration}}` first.
- Finish file-changing work by committing only task files, running required checks, merging into `{{git.integration}}`, and pushing when a remote exists. A latest explicit user instruction to not commit, push, merge, clean, or to pause overrides this default. Use a clean integration worktree if the shared `{{git.integration}}` checkout is dirty or busy. A resolvable file conflict is not by itself a reason to pause: read both sides, preserve both intended changes, resolve, and rerun relevant checks; ask only when the correct combined behavior is unclear or unsafe. After local and remote containment is verified, non-force remove only your clean task/integration worktrees and local/remote task branches created for the current task, except system-managed worktrees.
- At completion inspect and non-force clean only branches and agent-created worktrees that you created for the current task, after confirming they are clean and contained in pushed `{{git.integration}}`. System-managed or platform-provisioned worktrees are always retained and never require agent cleanup. Do not inspect, list, report, merge, clean, or otherwise manage other agents' branches/worktrees unless the user explicitly authorizes that exact action. Never merge uncommitted state, another repository's branch, secrets, or unintended generated files; never force, delete a dirty/active worktree, or remove unmerged work.

## 4. Implementation, Docs, And History

- Start with `AGENTS.md`, then current targets/callers and relevant current contracts. Implement the smallest coherent fix and preserve established module and layer boundaries. Follow the applicable local `AGENTS.md` for documentation, runtime, database, deployment, or app-specific procedures.
{{#codemap}}- `{{codemap.outDir}}/` is a generated code map (module × frontend/API/backend/database); never hand-edit its generated files. A Rust function's `///` comment ({{language}}, first paragraph a one-sentence summary) is the source of its description there; functions whose names already say what they do may go without one, but an existing `///` must be updated in the same change when the function's behavior changes. New backend or frontend files must match a module in {{modulesSource}}; run `vibedoc codemap generate` and check "未归属文件" in `{{codemap.outDir}}/INDEX.md`. Use `vibedoc codemap fn` and `vibedoc codemap route` to find callers, routes, and tables before changing code.
{{/codemap}}- `{{rulesDir}}/<module>.md` holds the user's own logic rules (module × layer) and outranks `{{docs.behavior}}/*` and other current docs. Never edit their titles or text, and never create, rename, move, or delete rule files; change rule state only through `vibedoc rules` (it rewrites managed status lines and refuses anything else). Act on rules only when the user asks (for example "同步规则 app-1" or "同步 app 的规则"): run `list`/`show`, propose a plan in chat and run `confirm <id>`, wait for the user's approval (or the board moving it to 进行中) before `start <id>`, implement, then `mark <id> --impl <functions>`. If code or docs conflict with a rule, ask in `{{docs.questions}}` (`vibedoc question add`) instead of changing the rule.
- `{{featuresDir}}/<module>.md` is the functional and architecture overview (no code details) that the AI writes and the user may edit. Keep it in step when a feature changes, and record each rewrite with `vibedoc features set <status> <id>` (`done` = merged into `{{git.integration}}`, `released` = live in production). A user edit shows as 已修改 and is a new request: act on it only when the user asks (for example "同步功能 app-f3"), following the same list/show → plan → `confirm` → approval → `doing` → `done` flow as rules. It does not override `{{docs.behavior}}/*` or API/table contracts. A feature the user asks for directly in chat (new, changed or removed user-facing behavior) goes into the same document too: add or update its item before implementing, `set confirm` while your plan waits for approval or `set doing` once work starts, `done` after merging into `{{git.integration}}`, and `released` when it reaches production; a removed feature's item is deleted. Internal work with no user-facing change (tooling, refactors, infrastructure, tests, docs) needs no item.
- `{{tablesDir}}/<schema>.md` holds table changes the user requests (new tables or changes to existing ones). Act on one only when the user asks (for example "同步表 billing-t1"): `vibedoc tables list|show` (show includes a SQL draft), propose a migration plan following the repository's migration conventions and `set confirm <id>`, wait for approval before `set doing`, write the migration, then `set done` after merging. The draft is a starting point; add permissions, indexes and policies the repository requires. Ask when an item conflicts with the current schema or rules; never edit the user's item text.
- User-provided requirements and UI sketches live in `{{docs.human}}/`. Read the relevant ones before feature or UI work and treat them as read-only originals; see `{{docs.root}}/AGENTS.md`.
- Record every completed change in a change log created with `vibedoc changelog new --role <role> --slug <slug>` (`{{docs.changelogs}}/<YYYY-MM-DD>/<HHMMSS>_<role>_<slug>.md`); open product questions go to `{{docs.questions}}` with `vibedoc question add`, and answered ones are resolved with `vibedoc question resolve` after the conclusion is written to `{{docs.behavior}}/*`.
